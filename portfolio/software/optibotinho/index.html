Code review

A review panel,
not a single opinion.

Every pull request is routed to a review tier. The tier's reviewers run in parallel through the Claude Code and Codex CLIs on a real checkout. A manager then checks their findings against the head commit and publishes one consolidated review.

Tiers by risk

Ordered rules on paths, sizes, labels and repositories pick how hard to look. Sensitive code gets the full panel; a docs typo gets a light one. The last tier always matches.

Real CLIs, real checkouts

Reviewers are Claude Code and Codex sessions with their own prompts and accounts, run by a separate review runtime. Profiles can add a code graph over MCP.

One verified review

The manager drops what it cannot confirm at the head commit, rates the rest from critical to low, and posts inline comments plus a check run. Drafts and empty diffs are skipped.

Review rounds

Round three remembers
round two.

Every push starts a new round at the current head. Findings are fingerprinted against earlier rounds, so the bot does not say the same thing twice, and the thread stays readable after ten pushes.

  • Novel, carried, duplicate, reintroduced. Each finding is labelled against history; duplicates are not posted again.
  • Old overviews fold away. The previous summary collapses to “Superseded by round N”, keeping the findings it had at the time.
  • Approval waits for open threads. A clean round with carried findings still unresolved does not approve.

Merge queue

Clean pull requests
merge themselves.

Configured rules put every pull request in one of three lanes. lane:auto merges after a clean AI review. lane:assist also needs enough human approval and a delay. lane:human is left to people. The queue automates; it does not enforce, so anyone can still merge by hand.

Merge attempts

Score, not count

Approvals are weighed by a score per GitHub user, with boosts per repository. The author's own approval never counts toward the threshold.

Rechecked before every merge

Head and base SHAs, mergeability, labels and kill switches are read again right before the merge call. Every attempt is recorded: merged, conflict, stale, blocked or merged by a person.

People keep the last word

lane:human is never removed, a WIP label holds the queue, and audited overrides can merge now, hold, force a lane or change the delay.

Commands

Mention it.
It answers.

Write @OptiBotinho and a command in any issue or pull request. The bot reacts with 👀 so you know it heard, does the work, and replies in the thread. Anything that is not a command gets an AI answer.

  • Pull requests. write drafts the title and body, review queues a review at the current head, approve approves.
  • Across repositories. clone an issue everywhere it applies; create, delete or copy labels and milestones in one comment.
  • Reports. Milestone progress, releases, team contributions and the project board, on request.

Chat

Mentions reach people
where they read.

A GitHub @mention becomes one more notification that is easy to miss. OptiBotinho also sends it as a direct message in the team chat, using a map from GitHub logins to chat users.

  • Every place a mention can hide. Pull request descriptions, conversation comments, review bodies and line comments.
  • Ready for testing. When issues reach Testing, assignees get one message per batch, not one per issue.
  • Never in the way. Messages go out from a queue, exactly once; a slow chat never delays the rest of the webhook.

Production errors

One cause.
One issue.

Laravel Nightwatch reports exceptions per application, so a Redis restart seen by ten apps is ten reports. OptiBotinho classifies each one before filing anything, fingerprints the cause, and links repeats to the issue that already tracks it.

Nightwatch webhooksissue.opened
GitHub issues

Four categories

Application errors go to the repository that saw them. Infrastructure and external dependency failures go to the platform repository. The monitoring agent's own noise is dropped.

Fingerprinted causes

Messages are normalised before matching, so the same failure with a different id, path or timestamp joins the open issue as a comment.

Triage, then follow-up

A triage dashboard tracks reports by category and cause. Resolving or ignoring an error in Nightwatch closes the GitHub issue, and a backfill command sorts out the issues filed before triage existed.
