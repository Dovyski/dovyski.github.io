Every merged fix needs someone to try it.
The Testing column is where issues wait.

A fix is merged, deployed to stage and moved to Testing. Then someone has to read the issue, work out what to check, log in, click through it, take screenshots and write it up. Across many apps that is a full-time queue, and a quick retest is the easiest thing to put off. OptiQazinho takes that queue and works it like a tester would.

Traced to a claim

Each case checks something the issue or the pull request says: the happy path, the correctness of the result, and anomalous input with its error message.

Asks before rewriting

When an issue already has test cases that look weak, it comments first with what it wants to change and why, and edits them only if nobody objects.

Asks when unsure

Missing information or contradicting details get a question in the issue and the ai:question label. It comes back to the issue for the answer.

Execution on stage

It uses the app
the way a person would.

The fix is tested where it was deployed, not in a unit test. OptiQazinho opens the app in a real Chrome through Playwright, clicks, types and reads the page, checks each case, and keeps screenshots, browser logs and recordings along the way.

A real browser

Google Chrome is baked into the tester image, with Chromium as a fallback. The page is read from snapshots with element references, so clicks target elements, not pixel positions.

User-level checks only

It never runs the unit or integration tests, even when the issue asks for them, and never reads CI results. CI owns those. QA owns what a user sees on stage.

Evidence as it goes

Screenshots, console output and recordings are kept for every case, and above all for failures, so the report can show what happened.

Permissions

Two accounts,
two browser sessions.

Authorization, isolation between users and rendering across accounts are always tested with two stage accounts, each in its own browser session. Routes that only take a bearer are called with a token minted per account.

  • Try before blocking. A check is marked blocked only after logging in or minting the token failed, and the report says what was tried and which status came back.
  • Accounts by role. Test cases and comments name the accounts by what they are, never by their password.
  • Credentials stay in. Passwords and tokens never reach an issue, a log or a screenshot; requests are shown with Bearer <redacted>.

Two verdicts

No problem: qa:ok and ai:done. A problem: qa:problem, the issue goes back to Redo. Either way it unassigns itself when the pass ends.

Evidence anyone can open

Every screenshot or video it cites is uploaded and embedded, with a description written for someone who cannot see it. Never a path on its own disk.

Written for the other testers

Human testers may be on the same issue. It reads their comments first, builds on them, and leaves a clear picture of what passed, what failed and what is missing.

Chat

Ask for a test in chat.
Hear back there too.

Anyone on the team can message OptiQazinho with an issue link or an app name and a number. The test is queued at once, the reply says when it will run, and the outcome comes back to the chat that asked.

  • Status in human terms. “I'll get to #5904 after the mail retest.” Never a job id, a queue position or a machine name.
  • Steer or cancel a running test. An extra check or a login hint reaches the test at its next step; a cancel stops it at the next safe point.
  • Says what is missing. An issue without the ai:testing label or the Testing status gets told so, instead of a silent no-op.

Swept and requested

Each tester sweeps its repository on a schedule for issues labelled ai:testing in Testing, and runs chat requests without waiting for the next sweep. A new edit or comment makes a tested issue eligible again.

Deploys do not lose a test

A deploy marks the running job interrupted and the new container runs it again. Every comment carries a hidden marker, so the retry continues where the last attempt stopped instead of posting twice.

Stays in its lane

A tester only touches issues of its own repository, even when others share the board. A small control file can pause a tester or skip an issue, applied at the next safe step.
